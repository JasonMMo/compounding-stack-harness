# Positioning — compounding-stack-harness

> 사내망을 벗어나지 않는 self-host 풀스택 codegen. 도메인 전문가 AI 가 업무를 인터뷰하고, 고객사가 고른 Frontend + Backend 조합으로 시스템이 완성된다.

---

## 1. Audience — Why 3 Personas

이 product 의 구매·사용·운영 라인은 한 사람이 아닌 세 사람이 동시에 잡는다.

**CEO (의사결정자)** 는 "왜 이게 필요한가"와 "얼마인가"를 결정한다. 코드를 보지 않는다.

**업무담당자 (현장 사용자)** 는 "실제로 우리 일을 이게 대신하는가"를 검증한다. 시스템 교육 없이 쓸 수 있어야 한다.

**IT-담당자 (운영자)** 는 "사내망에 올릴 수 있는가"와 "보안·SSO·백업은 우리 기준을 맞추는가"를 심사한다.

세 사람 모두 "Yes" 라고 말해야 계약이 된다. 한 명이라도 거부하면 성사되지 않는다. 그러므로 모든 milestone 의 인수 기준은 세 사람 각각의 행동으로 표현된다 — 코드 완성 여부가 아니라.

## 2. Persona Cards

### Persona A — 고객사 CEO (의사결정자)

**Who**: 비상장 중소·중견기업 대표 또는 본부장급. 직원 50~500명.

**조직 맥락**: IT 부서가 1~3명이거나 아예 없다. 외주 SI 에 반복 비용을 쓰고 있거나, 엑셀·그룹웨어로 간신히 버티는 상황. "자체 시스템을 갖고 싶지만 개발팀을 뽑을 여력이 없다"는 문장이 정확하게 해당된다.

**매일 무엇으로 고통받는가**:
1. 외주 SI 한 번에 수천만 원, 납기 6개월, 끝나면 유지보수 의존.
2. SaaS 구독은 데이터가 외부 클라우드에 올라가는 것이 불안 (금융·의료·제조 규제).
3. 개발자 채용 비용 vs 개발자 없는 현실 사이에서 무한 대기.

**우리 product 가 그들에게 무엇을 약속하는가**: 외주 없이 사내 시스템을 만들고, 데이터는 사내망에서 벗어나지 않는다. 연간 라이선스 하나로 도메인 무제한.

**"성공"이 어떻게 보이는가**: 계약 체결 후 4주 이내에 영업·재고·고객관리 중 하나가 실제로 돌아가고, 직원들이 쓰고 있다. 외주 SI 없이.

**milestone 별 첫 만남**: M1 에서 데모 영상을 보고 trial 신청. M2 에서 계약서 서명.

---

### Persona B — 업무담당자 (현장 사용자)

**Who**: 영업팀장, 관리팀 주임, 재고 담당 대리 등 특정 업무 도메인을 실질적으로 운영하는 사람. IT 지식 없음.

**조직 맥락**: 매일 엑셀 시트 3~5개를 동시에 열고 수작업으로 집계한다. 데이터 오류가 남의 책임인지 내 책임인지 매번 논쟁한다. 새 시스템이 도입되면 "또 배워야 하나" 가 첫 반응.

**매일 무엇으로 고통받는가**:
1. 반복 입력: 같은 데이터를 엑셀 A, 그룹웨어 B, 보고서 C 에 세 번 입력.
2. 조회 불가: "지난달 특정 거래처 주문 합계"를 뽑으려면 필터 30번.
3. 히스토리 소실: 퇴사자의 엑셀이 삭제되면 1년치 기록이 사라짐.

**우리 product 가 그들에게 무엇을 약속하는가**: AI 가 "우리 회사 영업은 어떻게 돌아가나요?" 를 물어보고 그 대답으로 화면을 만든다. 코드 한 줄 안 봐도 된다. 기존 업무 방식을 바꾸지 않아도 된다 — 시스템이 우리 방식을 따른다.

**"성공"이 어떻게 보이는가**: 인터뷰 세션 1회 (1~2시간) 후 자기 업무 화면 초안이 나온다. 그 화면으로 실제 업무 데이터를 입력해 보고 "맞다" 또는 "이건 달라" 를 말할 수 있다.

**milestone 별 첫 만남**: M1 데모에서 generic 도메인 화면을 보고 "우리 회사 것도 이렇게 되나?" 질문. M2 에서 실제 인터뷰에 참여해 자기 도메인 화면 초안 수령.

---

### Persona C — IT-담당자 (운영자)

**Who**: 전산실 1~2명, 또는 외부 IT 파트너사 담당자. 보안 정책·서버 운영·SSO 연동을 책임진다. "도입하면 내가 관리해야 한다"는 사람.

**조직 맥락**: 사내 보안 정책 (데이터 외부 반출 금지, ActiveDirectory/LDAP SSO 필수, 정기 감사로그 요구) 을 맞춰야 한다. 도입 실패 시 책임자가 본인이다.

**매일 무엇으로 고통받는가**:
1. 외산 SaaS 도입 요청이 올 때마다 "보안 검토해라" — 검토만 3개월, 결국 반려.
2. 사내 시스템 운영 문서가 없어서 담당자 교체 때마다 파악에 2개월.
3. 어떤 tool 이든 SSO 연동이 안 되면 별도 계정 관리 부담 → 보안 홀.

**우리 product 가 그들에게 무엇을 약속하는가**: `docker-compose up` 한 번. Vault Agent + Keycloak SSO 사이드카 포함. 데이터는 고객사 서버 밖으로 나가지 않는다. 감사로그·접근권한·SSO 는 기본 탑재. 새 adapter 추가는 compliance test 통과가 유일한 조건.

**"성공"이 어떻게 보이는가**: 자사 Linux 서버에 `docker-compose up` 후 30분 이내에 SSO 로그인이 되고, 감사로그가 적재된다. 운영 문서는 자동 생성.

**milestone 별 첫 만남**: M1 에서 ops pack (docker-compose + Vault + SSO) 문서를 보고 보안 검토. M2 에서 실제 사내 서버에 배포·검증.

## 3. Positioning Statement

사내망 데이터 반출이 불가하고 IT 인력이 부족한 한국 중소·중견기업을 위해, 우리는 self-host 풀스택 codegen 하네스를 제공한다. 이 하네스는 AI 도메인 전문가가 업무담당자를 인터뷰해서 고객사 맞춤 풀스택 시스템을 생성하고, Frontend · Backend 를 고객사가 선택한 조합으로 교체할 수 있다는 점에서 범용 SaaS · 외주 SI 와 다르다. 우리의 근거는 14 공통 도메인 preset · 4계층 자동 테스트 · ops pack (Vault + SSO 포함) 이 첫 배포부터 함께 제공된다는 실측 구현이다.

## 4. Differentiation — 3대 차별화 재진술

### 차별화 1 — Axis-7 Expert-Agent: 도메인 전문가 영입 없이

CEO 관점: 산업별 전문가 인건비 없이 영업·재고·의료·제조 도메인의 "관습" 을 시스템에 박을 수 있다.

업무담당자 관점: "우리 회사 방식"을 말로 설명하면 AI 가 받아 적어 시스템을 만든다. 컨설턴트를 고용하거나 RFP 를 쓸 필요가 없다.

IT-담당자 관점: domain-expert agent 는 사내망에서 돌아가는 로컬 추론 경로를 지원한다 (인터넷으로 업무 데이터가 빠져나가지 않는다).

### 차별화 2 — Pluggable F/B: 우리가 고른 기술 스택으로

CEO 관점: "다음에 기술 바꾸면 또 돈 드나?" 가 없다. customer profile YAML 2줄만 바꾸면 같은 도메인이 다른 스택으로 동작한다.

업무담당자 관점: 화면이 회사 표준 포털 (Nexacro / React / 사내 그룹웨어 연동) 에 맞춰 나온다. "새 시스템이라 화면이 낯설다"는 반발이 줄어든다.

IT-담당자 관점: Backend 를 Java EE javax (기존 WAS), Spring Boot Jakarta (신규), FastAPI (AI 연동 팀) 중 하나로 지정할 수 있다. 기존 인프라에 얹힌다. 새 WAS 를 도입할 이유가 없다.

### 차별화 3 — Cost-Aware by Design: 숨겨진 비용이 없다

CEO 관점: 연간 라이선스 외 AI API 비용이 per-request 측정되어 월 보고서로 나온다. "나중에 청구서 보고 놀란다"가 없다.

업무담당자 관점: 대화형 인터뷰는 저비용 호출, 코드 생성은 필요할 때만 — 사용하지 않는 기능에 돈이 안 나간다.

IT-담당자 관점: multi-provider fallback, prompt cache, batch 모드가 기본 내장. 특정 LLM provider 에 종속되지 않는다. LLM provider 교체는 CTO 단독 결정 사항이고, 비용이 일정 임계를 넘으면 자동 대안 경로가 동작한다.

## 5. Milestone Acceptance Triples (G-7 Satisfaction)

아래 6개 라인이 `docs/business/revenue-roadmap.md` 의 각 milestone `gating` 항목에 **페르소나 인수** 필드로 추가되어야 한다.

```
M0 — Founding
**페르소나 인수**: CEO 와 IT-담당자 역할을 겸하는 창업 팀이 헌장·아키텍처·비용 모니터링 문서를 읽고 7축 구조와 revenue gate 를 30분 안에 설명할 수 있다.

M1 — Generic Harness Baseline
**페르소나 인수**: IT-담당자 가 ops pack (docker-compose + Vault + SSO) 을 처음 받아 사내 Linux 서버에 배포하고, 14 도메인 중 1개 데모 화면에 SSO 로그인으로 접속하는 전 과정을 2시간 안에 완료한다.

M2 — First Paid Customer
**페르소나 인수**: 업무담당자 가 domain-expert agent 와 인터뷰 세션 1회 (최대 2시간) 를 완료하고, 자기 회사 핵심 도메인 1개의 CRUD 화면 초안을 당일 수령하여 실제 업무 데이터를 입력해 본다.

M3 — Expert-Agent First Vertical
**페르소나 인수**: 특정 산업의 업무담당자 가 해당 산업 전용 domain-expert agent 와 인터뷰 후, 산업 특화 필드 (예: 의료 ICD-10 코드, 금융 계정과목) 가 포함된 화면 초안을 1주일 안에 수령하고 "기존 업무 방식과 맞다"고 확인한다.

M4 — 3 Vertical + Marketplace Alpha
**페르소나 인수**: 외부 contributor (IT-담당자 또는 도메인 전문가) 가 새 industry preset PR 을 제출하고, 4계층 자동 테스트 + 산업 컨벤션 가드를 통과하여 머지 승인을 3일 안에 받는다.

M5 — Multi-Tenant SaaS
**페르소나 인수**: CEO 가 SaaS 플랜 landing page 에서 trial 신청 후, IT-담당자 개입 없이 테넌트 프로비저닝이 완료되고 업무담당자 가 첫 로그인해서 도메인 선택 화면을 보는 전 과정이 1시간 안에 끝난다.
```

## CEO 회수 질문 답변 (Growth-5e, 2026-05-29)

- **Q1 (가격대)**: $10k~$30k self-host license 옵션을 선호하나 **시스템 성숙도가 고객 기대치를 넘을 때까지 공개 보류** (CEO 결정, 2026-05-29). M2 첫 paid customer 협의 진입 시 CEO 가 maturity threshold 평가 → 공개 게이트.
- **Q2 (첫 vertical)**: 첫 paid customer 의 산업 = 첫 vertical (charter §2 게이트 이미 합의). 사전 선택 없음.
- **Q3 (OSS/상용 분리선)**: M2 첫 고객 협의 종료 후 결정 — charter v1.3 의 public 전환 게이트와 자연 정렬.
- **Q4 (M3 vertical landing 책임자)**: CMO copy + CDO visual 협업. charter §2 decision matrix 의 `landing/portal 비주얼 = CDO` + `sales enablement = CMO (CDO 협업)` 매핑 활용.

## 6. Open Questions for CEO

- **가격 앵커 (anchor pricing)**: 연간 라이선스 "\$10K~" 에서 "\$10K" 가 anchor 인가 "\$30K" 가 anchor 인가. 첫 고객사와의 협상 직전까지는 공개 페이지에 숫자를 노출하지 않는 것이 유리할 수 있다. "가격 문의" CTA 전략과 비교해 CEO 가 결정.

- **trial 범위와 case study 권리**: 현재 정책은 "M2 까지 3개사 무료, case study 권리 양도". case study 를 실명 공개할지 익명 처리할지, 고객사 산업 정보가 경쟁사에 노출되는 리스크를 어떻게 완화할지 — CEO 가 고객 계약서 초안 시 확정 필요.

- **sales motion (inbound vs outbound)**: M1 데모 영상 + GitHub README 로 inbound 를 기다리는 전략 vs CEO 가 직접 LinkedIn/커뮤니티에서 첫 고객 5개사를 아웃바운드로 접촉하는 전략. M2 까지 매출이 발생하지 않으면 M3 진입이 지연된다 — 어느 쪽에 집중할지 CEO 판단.

- **첫 vertical 조기 가설 vs 데이터 우선**: 현재 정책은 "M2 첫 고객 산업 = M3 vertical 자동 결정". 그러나 CMO 관점에서 특정 산업 (제조 MES, 의료 EMR, 물류 WMS) 에 선제적으로 메시지를 맞추면 inbound 효율이 높아질 가능성이 있다. CEO + CTO + CMO 3자 합의 필요.
